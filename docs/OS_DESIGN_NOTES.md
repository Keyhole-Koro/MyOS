# MyKernel OS 設計書 / 注意事項 (Design Notes)

## 1. スケジューラのタスク管理 (Task Management)
* **設計判断**: 動的メモリ確保（リスト構造）ではなく、**固定長配列 (`MAX_TASKS = 256`)** を採用。
* **理由**: 
  * 割り込みハンドラ内でのヒープ確保(`malloc`/`heap.alloc`)は非常に遅く、予測不可能であるため。
  * リストのポインタ操作ミスによるカーネルパニック（システム即死）を回避するため。
  * メモリ上に連続して並ぶ配列の方が、CPUのキャッシュヒット率が高く、爆速でコンテキストスイッチが可能であるため。
* **仕様**: 
  * 最大タスク数は `MAX_TASKS` で制限。
  * `task_state`: `0` = RUNNABLE (実行可能), `1` = SLEEPING (睡眠中), `2` = EMPTY (空き枠)

## 2. スリープの仕組み (Sleep & Wait)
* **設計判断**: `halt_cpu()` ではなく、**タイマー割り込みと状態フラグを用いたビジーループ**を採用。
* **理由**:
  * 現在のエミュレータ(MyEmulator)では、`halt` 命令は「割り込み待ち」ではなく「マシンの電源OFF（エミュレータ終了）」として実装されているため。
  * ソフトウェア割り込み(`SWI`)等の明示的なYield（CPUを譲る）命令が存在しない。そのため、スリープ関数内での極小ビジーループ (`while(state==SLEEPING){}`) に入ることで、次のタイマー割り込み発生時にスケジューラが自動で別のタスクへ処理を移す仕組み（自タスクの実質的なCPU使用率0%）を実現している。

## 3. UIとイベント処理 (Event-Driven UI)
* **設計判断**: UIの更新ループ内でハードウェアレジスタを直接ポーリングするのではなく、**イベントキュー（リングバッファ）**を採用。
* **理由**:
  * 割り込み処理（ISR）は「一瞬で終わらせる」鉄則を守るため。ISR内ではキューに値を積む（Push）だけの処理に留める。
  * UIの描画など重い処理を行っている裏で発生したハードウェア割り込み（マウスやキーボード入力）を取りこぼさないようにするため。
* **仕様**:
  * キューは固定長のリングバッファで実装（メモリの再確保が不要で安全・高速）。

## 4. コンテキストスイッチの仕組み (Context Switching & Stacks)
* **設計判断**: 全タスクが完全に独立した自身のスタック領域を保持し、割り込みのトランポリン内で `sp` (スタックポインタ) 自体をすり替える方式を採用。
* **理由**:
  * 複数タスク間で状態を安全かつ確実に保持するため。1つの巨大なスタックに全タスクの状態を積み上げる方式（LIFO）だと、A→B→C のような柔軟なタスク切り替えが不可能になり、過去のタスクのローカル変数や呼び出し履歴が破壊される。
* **仕様**:
  * `spawn_task` 時にタスク専用のスタック領域 (例: 1024 bytes) をヒープから割り当てる。
  * 割り込み発生時、ハードウェア (`PC`, `SR`) および トランポリン (`r0-r7`等) は **「中断されたタスクのスタックの現在の位置 (`sp`)」** にそのまま退避（Push）される。スタックの根本から上書きされるわけではなく、使用中の最前線から間借りするためアプリの既存データは安全。
  * スケジューラが次のタスクを決定すると、トランポリン内で `mov sp, r1` が実行され、**「CPUが参照するスタックの場所」自体が別タスクのスタックへと切り替わる**。
  * その直後に行われる `pop` や `iret` は「新しいタスクのスタック」に対して行われるため、以前そのタスクが中断された時の状態が完璧に復元され、タスクが再開される。
